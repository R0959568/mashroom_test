## Trade-offs to defend
- EDA computes aggregates on the server and pulls one sample, instead of loading data into pandas : 212 M rows do not fit in laptop memory; group-bys over all trips take 8-80 s on the server.
- Sample = trips of 2025 whose ride_id ends in `00` (~0.4 %, 178,652 trips) : one complete, recent year covers every season; deterministic so the findings stay reproducible.
- Mann-Whitney U instead of a t-test for trip duration : durations are strongly right-skewed (median 8-13 min, max ~24 h); a rank test makes no normality assumption.
- Effect sizes (rank-biserial r, Cramer's V, Spearman rho) reported next to p-values : with n in the hundreds of thousands or millions every p-value is ~0; the chi-square test on bike type x user type is "significant" with a negligible V = 0.049.
- Watermark = start time of the last **successful** run (not a per-file manifest) : a re-uploaded month is detected because its S3 LastModified moves; a failed run leaves the watermark, so the retry is automatic; idempotency comes from overwriting a month's Parquet file.
- `MinYear = 2021` on top of the date filter : the 2013–2020 bundles were re-uploaded in 2024, a date filter alone would pull the old column layout into the v2 folder.
- `X-Admin-Token` on POST only : the subdomain is public and a run downloads gigabytes; reads stay open for the team. A per-user identity would need a login layer the project does not have.
- Conversion inside the API container : simpler ops and reuse of tested Python, at the cost of a ~400 MB larger image and CPU shared with an API that only serves metadata today.
- H-A test pairs each of the last 12 months with the same calendar month a year earlier instead of a trend test over all 68 months : the season drops out of every difference and the steep 2021-2024 rise cannot dominate (the caveat 02 §3.2 raised itself); Wilcoxon because 12 differences are too few to check normality.
- MAE instead of MAPE as the main model metric : MAPE on Jan-Aug 2026 is 42-43 % against a median APE of 19 %, inflated by a few snowstorm days with a few thousand trips.
- Holidays stored once (211 rows for 2021-2028, one row per date through the `calendar_day` view) and joined on the trip date, never written per trip : 212 M trips × a flag would be redundant; the package runs only when the calendar is (re)loaded.
- A calendar load replaces the years it covers (delete + insert) instead of an upsert : a holiday that a newer package version renames or drops would otherwise linger; an empty, duplicate or out-of-range export fails before anything is deleted.
- `holidays==0.105` pinned and `source_version` stored per row : the package encodes the rules in code, so a new version can change the data; the pin makes a change deliberate and the column makes it traceable.
- One global gradient-boosting model over ~2.400 stations instead of 2.400 per-station models : the global model learns the shared seasons, calendar and weather once and handles new stations; the price is that a station with an unusual pattern is pulled towards the average, which the per-station comparison on a few busy stations must make visible.
- Two direct targets (trips tomorrow, trips until the end of the month) instead of daily forecasts summed recursively : one measurable error per horizon and no compounding; the rest-of-month model gets no weather because no forecast exists that far ahead, the day-ahead model does.
- WAPE next to RMSE and MAE for the station-level evaluation : stations differ by an order of magnitude in volume, so MAPE explodes on small stations while a plain MAE is dominated by the big ones; WAPE weights errors by actual volume.
- Lags partitioned by station **and** active period, not by station alone : a station reopened after a gap of more than 60 days must not see "last week" in its previous period; its lags are NULL until it has 28 days again, exactly the cold start the API will face.
- One row per station and **target** day (the forecast for t made on the evening of t - 1), so `lag_7` is the same weekday last week relative to the target, as in 03 §6.2 : the API takes a station and a date and answers for that date; the alternative (one row per forecast origin) shifts every lag by one and makes the baselines harder to read.
- The rest-of-month horizon is 1 to 31 days long (from the target day to its month end) and the ridge model predicts a rate per remaining day, multiplied back before scoring : one scale for the coefficients; the transformation is undone before the error is measured, as the course recipe asks.
- Every rule baseline defined on every scorable row through fallbacks (last week's pace where a station has no usable year earlier) : the methods are compared on exactly the same rows; the number of fallback rows is printed so the reader sees the cost.
- Weather gaps (23 wind, 4 snow depth) filled with the last observed value : a feature may only look backwards; the first day is complete, so nothing stays empty.
- The whole feature table pulled once through `COPY ... TO STDOUT` and cached as Parquet : pg8000 is pure Python, 3,9 M rows through `pd.read_sql` would take many minutes; the Parquet file is also what goes to S3 for the SageMaker job.
- Ridge (L2 penalty, default alpha) rather than plain least squares for the linear floor, and no tuning of it : the lags of the same weekday over four weeks are strongly correlated, so unpenalised coefficients take large opposite values that change with the split; tuning the floor would only lift the bar that 06 - 08 must clear.
- The validation year 2025 goes into PyCaret as `test_data` and the real test period (2026) is never passed to it; the cross-validation is `fold_strategy="timeseries"` on rows sorted by day : PyCaret's default random split would train on the future; a fold block must be a period.
- The station key enters PyCaret as a categorical feature and is target-encoded (2.455 levels, above the one-hot limit) : the 6 October decision "station as a feature" without 2.455 dummy columns; the weekday and the month stay one-hot as in 05.
- The rest-of-month horizon is compared on the rate per remaining day and scored on the total : same reasoning as 05 §7; the leaderboard ranks on the rate, the refit table reports departures.
- PyCaret ranks on MAE; WAPE, RMSE and bias come from score_table() on the validation rows afterwards : a custom WAPE metric through add_metric() displayed 0,0 in PyCaret's tables while the same scorer called directly worked; not worth debugging when the final table is computed outside PyCaret anyway.
- The forecast's first call can take about 40 s : serverless endpoints without provisioned concurrency are what the Learner Lab budget allows and what notebook 11 chose; always-on endpoints would cost the lab's budget every hour of the remaining weeks for a demo that is used a few minutes a day. The SPA says the endpoint is waking up instead of looking stuck.
- The backend holds the forecast API's URL and key, not AWS credentials : the Learner Lab credentials rotate at every session, the API key of the HTTP API does not; the host can therefore never call SageMaker directly, only the API of 11.
- nginx must not depend on the citibike stack (resolver + variable, no upstream block) : one shared nginx for a production site and a course project is a coupling in itself; this keeps a failure of the project from reaching the site, at the price of no keepalive to the backend.
- The retraining pipeline retrains on the S3 snapshot of the model inputs and does not refresh them : the inputs are built from Postgres, which only the VPN reaches; a GitHub runner does not. Continuous training here means "a change to the training code leads to a retrained, gated, promoted model"; new data still goes through 07 §2 and 10 §1 on the laptop.
- The model pipeline depends on Learner Lab credentials in GitHub secrets that expire with every session : a run without a live session fails at its first step with what to refresh; the app pipeline does not depend on AWS at all, so an expired lab never blocks a deploy of the app.
